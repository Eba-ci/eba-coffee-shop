# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

EBA Coffee Shop - a French-language Next.js website for a coffee shop in Abidjan, Cote d'Ivoire. Full-stack TypeScript with PostgreSQL, authentication, and rich animations.

## Commands

```bash
pnpm dev              # Dev server (port 3000)
pnpm build            # Production build
pnpm start            # Start production server
pnpm lint             # ESLint
pnpm format:fix       # Prettier auto-format
pnpm db:generate      # Regenerate Prisma client
pnpm db:push          # Sync Prisma schema to database
pnpm db:studio        # Open Prisma Studio GUI
```

Package manager: **pnpm only** (do not use `bun` or `npm` — the repo relies on pnpm hoist patterns in `.npmrc` for HeroUI/Tailwind v4 to work).

Prisma client is auto-generated on `pnpm install` via the `postinstall` script.

Pre-commit hooks (Husky + lint-staged) run ESLint and Prettier on staged files automatically.

## Architecture

- **Runtime:** Node.js with pnpm + Next.js 16 App Router, React 19
- **Styling:** Tailwind CSS v4 (via `@tailwindcss/postcss`) + HeroUI component library with custom theme in `config/hero.ts`
- **Database:** PostgreSQL with Prisma ORM (`prisma/schema.prisma`), singleton client in `lib/prisma.ts`
- **Auth:** Better Auth (`lib/auth.ts` server, `lib/auth-client.ts` client), connexion du personnel par code e-mail (plugin `emailOTP`) + plugin `mcp` (OAuth pour Claude) ; pas de Google OAuth. API routes at `/api/auth/[...all]`
- **Animations:** GSAP (`@gsap/react`) and Framer Motion
- **Environment:** varlock for type-safe env vars; schema in `.env.schema`, types generated to `env.d.ts`

## Key Directories

- `app/(public)/` - Public pages route group with shared layout (navbar + footer)
- `components/(public)/` - Page-specific section components, organized by page name (e.g., `accueil/`, `a-propos/`)
- `components/layouts/` - Navbar, footer
- `components/providers.tsx` - Root providers (HeroUI)
- `config/` - Brand config (menu items), HeroUI theme, Prisma config
- `lib/` - Auth setup, Prisma client, utilities, JSON-LD structured data
- `generated/prisma/` - Auto-generated Prisma client (do not edit)

## Conventions

- **Path alias:** `@/*` maps to project root
- **Client components:** Explicitly marked with `'use client'`; most section components are server components
- **Formatting:** Semicolons, single quotes, 2-space tabs, arrow parens always (see `.prettierrc.json`)
- **Content language:** French (site targets Cote d'Ivoire market)
- **Theme colors:** Primary = deep purple, Secondary = golden orange, Background = cream/dark brown
- **Taille de fichier : 300 lignes max.** Au-delà, extraire en modules plus petits (composants enfants, helpers dans `lib/`) plutôt que laisser grossir. S'applique au nouveau code et à tout fichier substantiellement modifié ; ne déclenche pas de refactor rétroactif des fichiers existants qui dépassent déjà ce seuil hors du périmètre de la tâche en cours.

## État d'URL (nuqs)

- **nuqs = défaut** pour tout état porté par l'URL (filtres, tri, pagination, recherche). Plus de `useSearchParams` + `router.push` + `URLSearchParams` à la main dans le code neuf.
- **Une seule définition des parseurs par page** (`search-params.ts`, import depuis `nuqs/server`), partagée par le serveur (`createLoader`) et le client (`useQueryStates`) : valeur invalide → `null`/défaut des deux côtés. Modèle : `app/(dashboard)/dashboard/commandes/` (aussi `clients/`). **Un champ de recherche lit son `value` depuis l'état nuqs, jamais depuis une prop serveur recopiée dans un `useState`** : la réponse lente d'une requête écraserait ce que l'utilisateur a tapé depuis.
- `NuqsAdapter` est monté dans `app/(dashboard)/layout.tsx` (dashboard uniquement : le site public n'en a pas besoin, cf. « Performance du site public »). Une page hors dashboard qui adopte nuqs doit monter l'adaptateur elle-même.
- Quand la page lit la base selon l'URL : `shallow: false` + `startTransition` (état d'attente partagé), et `limitUrlUpdates: debounce(ms)` pour la saisie au clavier — l'état local reste instantané.
- **Paramètres communs** : `lib/url-state/shared-params.ts` (`pageParser`, `dateRangeParsers`, `rangeChangeToParams`) — utilisés par `components/(dashboard)/pagination.tsx` et `date-range-filter.tsx` (déjà sur nuqs), et réutilisés par `commandes/search-params.ts`. Une page qui a besoin d'autres paramètres les étend par spread plutôt que de les redéclarer.
- Restent sur `useSearchParams` + `router.push` (à migrer au fil de l'eau) : `depenses/{expense-filters,category-filter,articles-table,article-history-sheet}.tsx`, `investissements/source-filter.tsx`, `regularisations/mode-filter.tsx`, `cloture/closing-date-picker.tsx`, `menu/**` (filtres produits, stock-supplements). Ils cohabitent sans conflit avec nuqs : tous lisent l'URL réelle.

## UI library policy

- **HeroUI = défaut.** Tout composant interactif (Button, Input, Modal, Tabs, Card, Drawer, Select, Tooltip, Badge, Switch, Skeleton, etc.) utilise HeroUI.
- **shadcn (`components/ui/*`) = uniquement** pour les primitives que HeroUI ne couvre pas : `Sidebar`, `Breadcrumb`, `Table` data-dense, `Sheet` (snap-points spécifiques).
- Ne pas mélanger les deux dans un même composant sauf frontière claire (ex. layout shadcn + contenu HeroUI).
- Le thème HeroUI est dans `config/hero.ts` : `primary` (deep purple), `secondary` (golden orange).

## Animation policy

- **GSAP** : animations scroll-driven, timelines complexes, ScrollTrigger. Utiliser le hook `useScrollAnimation` (`lib/animations/use-scroll-animation.ts`) pour les patterns d'entrée ; GSAP brut pour les chorégraphies sur-mesure.
- **Framer Motion** : animations de présence (mount/unmount), hover/tap, `AnimatePresence`, micro-interactions React.
- **CSS** quand l'animation n'a ni état, ni geste, ni timeline : une entrée jouée une fois, une transition entre deux états figés. Ni GSAP ni Framer n'apportent quoi que ce soit là, et les deux coûtent du JS sur le chemin critique. Précédents : `.hero-rise` (`app/globals.css`, entrée du hero de l'accueil — il porte le LCP) et la bascule pilule/pleine-largeur de la navbar (`components/layouts/navbar.tsx`).
- **`m` et non `motion`.** `components/providers.tsx` monte `<LazyMotion features={domAnimation}>` — le jeu réduit de Framer, celui que HeroUI charge déjà. Écrire `motion.div` retélécharge le bundle COMPLET (drag + layout animations) **en plus** : ~24 Ko gzip par page. `domAnimation` couvre `animate`, `exit`/`AnimatePresence`, `variants`, `whileInView`, `whileHover`, `whileTap`, `whileFocus`. Un composant qui a réellement besoin de `layout` ou `drag` garde `motion` (il embarque ses propres features) — c'est le cas de `carte/_components/portion-composer.tsx` et des tables réordonnables du dashboard, tous déjà isolés hors des chunks initiaux.
- **`prefers-reduced-motion`** est obligatoire. GSAP via `gsap.matchMedia()` (déjà géré dans `useScrollAnimation`), Framer via `useReducedMotion()`, CSS via `@media (prefers-reduced-motion: reduce)`.

## Performance du site public

Le site vitrine est vu depuis Abidjan, en mobile, sur des liens où le **RTT pèse plus lourd que les octets**. Trois règles en découlent :

- **Aucun embed tiers ne se charge sans geste du visiteur.** Les intégrations tierces passent par une **façade** : un aperçu maison, et l'iframe monté au clic seulement. Deux implémentations, même patron — `_components/map-embed.tsx` (Google Maps, utilisé par l'accueil, `/le-lieu`, `/contact` et le suivi de commande) et `accueil/_components/tiktok-embed-lazy.tsx`. `loading="lazy"` ne suffit pas : le seuil de Chrome est large, et un simple passage de scroll déclenche tout. La façade est toujours un **vrai lien** (itinéraire Maps, page TikTok) : sans JS, ou en ctrl-clic, elle ouvre la destination. Vérifiable en listant les requêtes sortantes d'une page publique : la seule attendue est `googletagmanager.com`, et c'est **délibéré** — Consent Mode v2 impose que le conteneur parte pour que les balises puissent attendre le consentement (cf. `analytics/consent-boot.tsx`). Tout le reste — pixel Meta compris — ne part qu'après un « Tout accepter ».
- **Ce qui ne sert qu'au staff ne coûte rien à l'anonyme.** `authClient.useSession()` est **interdit** dans le layout public : il entrait dans le chunk de toutes les pages et lançait un `GET /api/auth/get-session` non cacheable pendant l'hydratation. Passer par `useStaffAccess` (`lib/hooks/use-staff-access.ts`), qui charge Better Auth en `import()` dynamique, au repos du navigateur. Le composant purement staff se monte derrière un `next/dynamic` (cf. `layouts/dashboard-fab-mount.tsx`) pour que son code sorte aussi du chunk initial.
- **Mesurer, pas supposer.** Le vrai chiffre est la somme gzip des `<script>` du HTML prérendu (`.next/server/app/<page>.html`), **hors** `noModule` que les navigateurs modernes ignorent. Le rapport de build de Next 16/Turbopack n'affiche plus le « First Load JS ».

## Ergonomie mobile

- **Cibles tactiles ≥ 24 px** (WCAG 2.2, 2.5.8 — niveau AA), et plutôt 44 px pour une icône seule. Une ligne de texte nue fait ~20 px : un lien de liste a besoin d'un `py-1.5`, une icône seule d'un conteneur `h-11 w-11`. Compenser dans l'espacement de la liste pour que la cible grandisse sans que le bloc enfle. **Exception** : les liens en ligne dans une phrase sont explicitement exemptés — ne pas les rembourrer, ça casse l'interlignage.

## Centralized schemas & constants

- **Zod schemas** : `lib/schemas/{order,menu,upload,expense,cash-closing}.ts` (+ réglages : `lib/loyalty-settings.ts`, `lib/pickup-settings.ts`) — utilise-les depuis les routes API ; les routes peuvent durcir via `.extend()` mais ne **redéclarent pas** inline.
- **Types métier partagés** : `lib/types/index.ts` (re-exports les types depuis les schémas).
- **Racine du site** : `lib/site-url.ts` — `siteUrl()` (varlock) et `normalizeSiteUrl()` (pur, pour les modules qui lisent `process.env`). Ne lis **jamais** `NEXT_PUBLIC_SITE_URL` directement pour construire une URL : la valeur est saisie à la main dans l'hébergeur et arrive presque toujours avec un slash final, ce qui produisait des `https://eba-coffee.com//a-propos` dans le sitemap, le `robots.txt`, `llms.txt` et le JSON-LD — pendant que les canonicals, résolus par `metadataBase` via `new URL()`, restaient corrects. Deux signaux contradictoires pour la même page. Test de non-régression : `app/sitemap.test.ts`.
- **Constantes** : `config/constants.ts` (`MAX_UPLOAD_SIZE_BYTES`, `SLOT_DURATION_MINUTES`, `OTP_TIMEOUT_SECONDS`, `ORDERS_PAGE_SIZE`, `ORDER_*_MAX`, etc.). Pas de magic numbers en doublon dans le code applicatif.
- **Recherche par nom** : `lib/search/trgm.ts` (`trgmSearch`) est le point d'entrée **unique** : la recherche est faite par **PostgreSQL** (extensions `pg_trgm` + `unaccent`, migration `20261024090000_add_pg_trgm_search` — lancer `pnpm db:push`), jamais en mémoire (Fuse.js a été retiré). Règle par mot saisi (ET entre mots, ordre indifférent) et par colonne : sous-chaîne accents/casse repliés, sinon `word_similarity ≥ 0,6` (fautes de frappe ; coupée sous 3 lettres). Score 0..1 pondéré par colonne. Chaque surface déclare ses colonnes : `lib/customers/page-query.ts` (liste clients, avec téléphone), `lib/inventory-search.ts`, `lib/expense-articles-search.ts`, `lib/menu/product-search.ts` (+ `lib/search/hits.ts` : `SELECT id, score … ORDER BY score`). Un champ de saisie dont les éléments sont déjà chargés dans l'écran passe par `useSearchHits` (`lib/hooks/use-search-hits.ts`, route `GET …/search?q=` via `lib/search/route.ts`) puis `itemsByHits`/`rankByHits` (`lib/search/rank.ts`) : la saisie reste un état local, jamais recopié depuis la réponse (sinon une réponse lente écrase la frappe). N'écris **jamais** un `filter(...toLowerCase().includes(...))` dans un composant. Surfaces restant à migrer : `lib/menu-display.ts`, `lib/catalog.ts` (`searchProducts`, caisse), `InventoryRefCombobox` (`articles-table.tsx`), le filtrage en mémoire de `lib/orders/search.ts`.

## Stock & commandes différées

- **Le stock est décompté à l'ENTRÉE EN CUISINE**, jamais à la création ni à l'encaissement. Point d'entrée unique : `sendOrderToKitchen` (`lib/order-mutations.ts`) ; verrou d'idempotence : `Order.stockReservedAt` (à sens unique, jamais remis à `null`).
  - **Exception** : une commande PUBLIQUE payée en ligne (Jèko), pour un retrait **aujourd'hui** (non différée), réserve son stock dès la **création** — pour toute la durée de la fenêtre de paiement (`PAYMENT_EXPIRY_MINUTES`, `config/constants.ts`), via le même `reserveStockOnce` (exporté pour `createOrder`, `lib/orders.ts`). Sans ça, un client au comptoir pouvait vendre l'article pendant qu'un paiement en ligne était en cours (incident réel avec des choux). Si le paiement n'arrive jamais, `expirePendingOrders` (`lib/jeko/expiry.ts`) restitue ce stock via `releaseUnpaidStockHold` et remet `stockReservedAt` à `null` — SEUL endroit autorisé à le faire, puisque rien n'a jamais été préparé pour une commande jamais payée.
- **Commande différée** = retrait un **jour civil ultérieur** (Abidjan). Prédicat UNIQUE : `isDeferredPickup` (`lib/orders/scheduling.ts`, pur, serveur **et** client). Une différée ne touche PAS au stock du jour : `createCashierOrder` ne l'envoie pas en cuisine (même règle que l'antidatage), `setOrderPayment` redevient purement financier, `payAndComplete` la refuse (409), et ni `cashier-queue` ni `getPublicOrder` ne la signalent en rupture.
- **Réservations par ressource (programmées du jour)** : une commande `NEW` **payée**, retrait **aujourd'hui**, sans remboursement actif, prend sa part du stock **produit par produit** dès qu'il est disponible (`lib/orders/stock-holds/`, table `OrderStockHold`) — sans entrer en cuisine (pas de notification « en préparation »). Le stock est décrémenté à la réservation (le comptoir ne peut plus le vendre). `reserveForScheduledOrders` (priorité : heure de retrait, puis création ; verrou de ligne par commande) est rejoué après chaque réappro / fixation de stock (`lib/menu/mutations/stock.ts`, option `reserveForScheduled: false` = « ce stock reste au comptoir »), après le paiement d'une commande non lancée et après l'édition de ses articles. Au lancement, `reserveStockOnce` ne décompte que `besoin − réservé` (`decrementResidualNeeds`) ; `computeShortage` déduit aussi le réservé. `releaseHolds` rend les parts à l'annulation, au dépaiement, à la remise en stock d'un remboursement total et à l'édition d'articles ; `releaseStaleHolds` balaie le reste (jour passé, remboursement actif). Lancer `pnpm db:push` (migration `20261022090000_add_order_stock_hold`). **Écrans** : `summarizeStockHolds` (`lib/orders/stock-holds/state.ts`) donne à chaque programmée payée du jour un `stockHold` (`full | partial | none`, ce qui attend) dans les files cuisine et caisse, et remplace le calcul de rupture naïf (le stock réservé est déjà sorti du stock courant : sans ça la commande s'afficherait « indisponible », y compris sur la page de suivi). `selectToLaunchToday` (`lib/orders/to-launch.ts`) range ces commandes en « prêtes à lancer » (tout est réservé) et « en attente de stock » : section en tête de `/dashboard/preparation` (visible même grille vide, carillon quand une commande devient prête, « Tout lancer » séquentiel avec confirmation de pénurie par commande) et mention dans la section « Programmées » de la caisse. La case « Programmées » du réappro (menu) décochée garde la fournée au comptoir. Aucun lancement automatique : le geste « Lancer la préparation » reste humain.
- **Pénurie au lancement** : jamais un mur. `sendOrderToKitchen`/`setOrderPayment`/`payAndComplete` acceptent `coverShortage` — le staff confirme avoir produit la quantité manquante, le serveur la crédite puis la réservation la redescend (net nul). La 409 porte la liste chiffrée des manques (`buildShortagePayload`), affichée par `useShortageConfirm`. **Personne ne doit passer par `/dashboard/menu` pour débloquer une commande.**
- **Paiement Jèko tardif** (commande déjà expirée, `CANCELLED` avec `paymentExpiresAt` encore renseigné) : `settleLatePayment` (`lib/jeko/settle-late.ts`) contrôle le stock (`getOrderShortage`, sauf commande différée). Stock OK → la commande est rétablie puis validée par `setOrderPayment` (issue `late_validated`). Sinon, ou si une récompense fidélité avait été utilisée (déjà restituée à l'expiration) → remboursement immédiat par `refundLatePayment` (`lib/jeko/refund.ts`) : contact + transfert Jèko (`lib/jeko/transfers.ts`) vers `customerPhone`, **produits seuls** (`onlineFee` conservé), référence déterministe `REMB-…` (un rejeu = 409 = « déjà parti »). Colonnes `Order.refund*` ; le solde Jèko (`summarizeOnlinePayments`) les déduit. Tout échec (numéro invalide, solde Jèko insuffisant, panne) → alerte staff « rembourser depuis le Dashboard Jèko », jamais de perte silencieuse. Une annulation faite par une personne (staff/client) garde l'ancien comportement (`late_payment`, alerte). Lancer `pnpm db:push` (migration `20261019090000_add_order_refund`) ; vérifier que la clé API Jèko a le droit Pay-out et que le solde du magasin couvre les remboursements. Le vrai transfert n'est pas testable en local (le mock `scripts/jeko-mock` l'imite).
- **Deux comptes Jèko** (plafond MENSUEL de 2 000 000 F d'encaissement par compte : un retrait ne le libère pas ; solde réel lu via `lib/jeko/balance.ts`) : `JEKO_*` = compte A, `JEKO_B_*` = compte B (`lib/jeko/accounts.ts`, `config.ts`). Le compte ACTIF (`JekoSettings`, `getActiveJekoConfig`, bascule admin dans `/dashboard/jeko`) ne sert qu'à CRÉER ou relancer un paiement ; `startJekoPayment` mémorise le compte sur `Order.jekoAccount`. **Tout appel Jèko sur une commande existante** (`reconcile`, `expiry`, `refund`, `send-jeko`, `refresh`, route `verifier`) doit passer `jekoConfig(parseJekoAccount(order.jekoAccount))`, JAMAIS le compte actif : un 404 d'un mauvais compte ferait annuler une commande payée. Le webhook essaie le secret de chaque compte (même URL) et `settleJekoTransaction(tx, account)` corrige `jekoAccount`. Soldes par compte : `getJekoLedger(account)`. Lancer `pnpm db:push` (migration `20261023090000_add_jeko_accounts`). Détail : `docs/paiement-en-ligne.md`.
- **Remboursements** (`lib/refunds/`, table `Refund`) : un remboursement est une ligne NÉGATIVE datée du jour où l'argent part (`payoutDate`) — la commande et ses `OrderPayment` ne sont jamais modifiés. Cycle : `REQUESTED` (caisse ou admin) → `APPROVED` (admin seulement, `REFUND_APPROVER_ROLES` dans `config/constants/refunds.ts` ; un admin peut demander ET approuver) → `PROCESSING` → `PAID` | `FAILED` | `UNCERTAIN`. Toute transition passe par `transitionRefund` (`updateMany` gardé sur le statut + journal `RefundEvent`) : idempotent. Plafond = `Σ OrderPayment − Σ remboursements actifs` (`getRefundCap`, verrou de ligne sur la commande à la création) ; les frais en ligne (`onlineFee`) ne sont jamais rendus. Mode d'envoi `JEKO_TRANSFER` (contact + transfert Jèko, `lib/refunds/send-jeko.ts`) ou `MANUAL` (remise en main propre, confirmée par la caisse). **Ne JAMAIS renvoyer automatiquement un transfert dont on ignore l'issue** : timeout / 5xx / 409 pendant le transfert → `UNCERTAIN`, un admin vérifie chez Jèko (`resolveUncertainRefund`) ; chaque essai prend une référence neuve `REMB-<id>-<essai>`. Une correction de numéro / canal (`updateRefundDestination`) repasse en `REQUESTED` : nouvelle validation admin. Le suivi des transferts `PROCESSING` est opportuniste (`refreshPendingRefunds`, appelé au chargement du dashboard, comme `expirePendingOrders`). À `PAID` (`settleRefundPaid`, une transaction) : remboursement total → tampon retiré ; « remettre en stock » (décoché par défaut, exige des lignes) → recrédit des lignes cochées ; push client. `setOrderPayment(false)` est refusé tant qu'un remboursement `PAID/PROCESSING/UNCERTAIN` existe. Le remboursement automatique d'un paiement Jèko tardif crée aussi une ligne `Refund` (`source AUTO_LATE`) ; les anciennes colonnes `Order.refund*` restent (prod) et le solde Jèko les ignore pour une commande qui a des lignes `Refund`. Échecs Jèko : `lib/jeko/transfer-errors.ts` (message + action conseillée). **CA net** : `revenue` / `revenueByPaymentMode` (`getDailyStats`, `getRangeStats`, `getDailySeries`) sont NETS — régularisations ajoutées, remboursements déduits ; `grossRevenue`, `grossRevenueByPaymentMode` et `refunds` sont exposés à côté. Source unique : `lib/refunds/aggregate.ts`. Un remboursement ne diminue le CA que si sa commande y est encore comptée (`isPaid` ∧ non annulée, évalué à la lecture : annuler ou dépayer ensuite ne déduit pas deux fois) ; la TRÉSORERIE compte toujours l'argent sorti (`sumCashRefundsForDay`, solde Jèko). **Clôture de caisse** : caisse théorique = fond + ventes espèces BRUTES − dépenses espèces − `cashRefunds` (figé dans `CashClosing.cashRefunds`) ; lire `grossRevenueByPaymentMode`, jamais le net, pour les ventes du tiroir. Stats clients : CA net calculé EN SQL dans la requête de la liste (`lib/customers/{filter,list,stats,stats-rules}.ts`) — la page est sélectionnée d'abord (filtre + tri + `LIMIT`), puis les chiffres ne sont calculés que pour ces ≤ 20 clients (`LATERAL`) ; seul un tri sur une stat agrège tous les clients. Le prédicat « commande comptée » (`stats-rules.ts`) doit rester identique à celui de l'index partiel `order_customer_counted_idx` (`prisma/sql/order-customer-counted-index.sql`, que Prisma ne sait pas décrire : `pnpm db:indexes`, appliqué par le CD après `db:push`). Stats de remboursements : `lib/refunds/stats.ts`. Données personnelles : `Refund` est dans l'export, l'anonymisation et la purge (`config/data-protection.ts`). MCP : `list_refunds`, `get_refund`, `get_refund_summary`, `create_refund` (DEMANDE seulement : valider/refuser/renvoyer exigent un admin identifié, dans l'application). **Remboursée en totalité et non récupérée** : la commande quitte la file caisse et la file cuisine (filtre à la lecture, `fullyRefundedOrderIds`, `lib/refunds/fully-refunded.ts`) sans changer de statut ; `settleRefundPaid` émet un `pg_notify('orders_changed')` pour que les écrans se mettent à jour (un remboursement ne touche pas la table `order`, le trigger ne sonne pas).
- **Édition d'articles** : sur une commande déjà réservée, `updateOrderItems` réaligne le stock dans les DEUX sens (décrément des ajouts, **recrédit des retraits**). L'invariant « jamais ré-incrémenté » ne concerne que les changements de **statut** (annulation, dépaiement), pas le contenu.
- **« À produire »** (écran cuisine) : dérivé des commandes, zéro saisie — `buildProductionPlan` (`lib/orders/production-plan.ts`, pur). Ne renvoie que les jours ayant des commandes.
- **Côté public**, un produit épuisé reste commandable mais contraint le retrait à J+1, via `effectiveItemAdvanceDays` (`lib/supplements.ts`) — on réutilise le canal `advanceOrderDays` du sélecteur de créneau plutôt que d'en créer un second. `createOrder` lève `SoldOutTodayError` si le retrait demandé tombe aujourd'hui.
- **Précommande par produit** : `Product.preorderable` (défaut `false` : **rien n'est précommandable tant qu'on ne l'active pas**, interrupteur « Précommande autorisée » dans l'onglet Disponibilité du produit, aussi via MCP `update_product`). `false` = le produit ne se commande **en ligne que pour le jour même** : pas de retrait différé (`isDeferredPickup`), et s'il est épuisé il ne passe PAS en précommande J+1 (`canOrderForLaterDay` le refuse, pas de bouton « Précommander »). Prédicat unique `isPreorderable` (`lib/supplements/availability.ts`) : un `advanceOrderDays` (produit ou catégorie) **l'emporte** — un produit qui ne se commande qu'à l'avance reste précommandable. Contrôle serveur (flux public uniquement, la caisse garde la main) : `assertPublicOrderConstraints` → `findNonPreorderableNames` (relu en base, jamais le snapshot du panier) → `PreorderNotAllowedError` / code `PREORDER_NOT_ALLOWED`. Côté client : `lib/cart-preorder.ts` (`sameDayOnlyItems`, `preorderConflictMessage` pour un panier qui mélange « jour même » et « autre jour »), jours masqués dans `SlotPicker`, et « Tout garder, retrait demain » masqué dans `SoldOutResolver`. Lancer `pnpm db:push` (ou la migration `20260901090000_add_product_preorderable`) après déploiement : **tous les produits existants passent en « pas de précommande »** et doivent être réactivés un à un.
- **`SupplementRules.ignoreSoldOut`** : sans ce drapeau, `lib/supplements.ts` retire SILENCIEUSEMENT un goût épuisé de la sélection. Toute surface qui autorise un goût épuisé doit le passer à `groupSelectionCount`/`isGroupValid`/`canSubmitSelections`/`getSelectedSupplements` — les quatre, sinon un goût validé à l'écran disparaît à l'ajout.

## Historique du stock

- **Quoi** : chaque mouvement de `Product.stockQuantity` et `SupplementOption.stockQuantity` laisse une ligne `StockMovement` (table `stock_movement`, append-only) : `delta` signé, `before` → `after`, `reason`, `source` (`STAFF` / `MCP` / `SYSTEM`), commande ou remboursement lié, `actorId`, nom figé (`label`). Pas de FK vers la cible ni la commande : produit, option ou commande peuvent disparaître, l'historique reste lisible. Stock illimité (`null`) : `before`/`after` à null mais `delta` conservé (on voit ce qui se vend).
- **Seul écrivain** : `lib/stock-history/record.ts` (`logStockChange` pour une variation relative déjà appliquée, `logStockSet` pour une valeur posée, `logStockAnomaly`) ; `lifecycle.ts` pour création et suppression d'options. À appeler **dans la transaction du mouvement, APRÈS l'écriture** (la valeur finale est relue). **Toute nouvelle écriture de stock doit journaliser** : sans ça le contrôle d'angles morts (`lib/stock-history/audit.ts`, page et MCP `get_stock_audit`) détecte la dérive. Réglages absolus : `lockStock` (`lock.ts`, `FOR UPDATE`) avant l'écriture, jamais `findUnique` puis `update`.
- **Acteur et source** : `StockLogCtx` en paramètre quand l'appelant le connaît (`orderId`, `actorId`) ; sinon contexte ambiant `runWithStockContext` (`source-context.ts`) : le handler MCP et l'assistant l'ouvrent en `MCP`, les server actions du menu et la route caisse `restock` en `STAFF` avec l'id de la session. Passages automatiques (réservation des programmées, expiration Jèko) : `SYSTEM`.
- **Motifs** (`STOCK_REASON_LABELS`) : vente au lancement (`ORDER_KITCHEN`), réservation / restitution des programmées (`HOLD_*`), édition d'articles (`ORDER_EDIT_*`), production déclarée (`SHORTAGE_COVER`, effet net nul mais visible), remise en stock de remboursement, expiration, réappro / réglage manuel / lot / formulaire, création, `OPTION_REMOVED` (supprimer ou **renommer** une option la recrée : son stock disparaît, tracé), `BASELINE`, `ANOMALY` (stock non rendu : goût introuvable ou désactivé au retrait d'un article ou au restock d'un remboursement).
- **Écran** : `/dashboard/menu/historique-stock` (onglet du menu ; `requireRoleOrAnalyst(MENU)`, lecture seule pour l'analyste ; modèle `commandes/` avec nuqs). Filtres : dates, motif, origine, recherche par nom (`pg_trgm` sur `label`), ressource (lien « Historique » des tableaux de stock), commande. Résumé par motif, tableau + cartes mobiles, panneau « Angles morts » (écarts avec le journal, stocks sans relevé de départ, négatifs, réservations orphelines, anomalies).
- **Règles ajoutées** : un restock manuel (`restockProduct/Option`) ne peut plus faire passer le stock sous 0 ; `bulkSetProductStock` relance la réservation des programmées comme `setProductStock`.
- **MCP** : `list_stock_movements`, `get_stock_history_summary`, `get_stock_audit` (lecture seule, donc ouverts à l'ANALYSTE).
- **Après déploiement** : `pnpm db:push` (migration `20261028090000_add_stock_movement`), puis le **relevé de départ** : bouton « Poser le relevé de départ » (ADMIN/MANAGER) ou `pnpm db:backfill-stock-baseline`. Idempotent. Avant lui, l'historique n'a pas de point de départ.
- **Limites connues** : l'ordre de deux mouvements dans la même milliseconde repose sur l'id (le contrôle de dérive peut signaler un faux écart pendant une vente en cours) ; une annulation après lancement ne rend pas le stock (voulu) et n'écrit donc aucune ligne.

## Avoirs (solde client)

- **Quoi** : un remboursement peut se faire en **avoir** (`RefundDelivery.STORE_CREDIT`, canal `AVOIR`) au lieu de rendre l'argent. Le montant rejoint `Customer.creditBalance` (clé = téléphone, pas de compte) à `PAID`, dans la même transaction (`settleRefundPaid`) ; un admin valide comme tout remboursement (`approveRefund` crédite aussitôt, rien à envoyer). Pas d'expiration. Une commande sans client (sans numéro) ne peut pas donner d'avoir. Code : `lib/credits/` (`ledger.ts` = **seul** point d'écriture du solde, verrou de ligne + journal `CustomerCreditEntry` ; `apply.ts` règle pure ; `spend.ts` prise/restitution par commande ; `offer.ts`/`public-offer.ts` propositions), réglages `lib/credit-settings*.ts` (Paramètres, MCP `get/update_credit_settings`).
- **Règle d'usage** (serveur ET client, `computeCreditApplication`) : `A = max(0, min(solde, total − reste minimum, ⌊total × plafond %⌋))`, défauts 1 500 F et 70 %. Toujours **recalculée côté serveur** (`setOrderCredit`), jamais crue du navigateur.
- **Un avoir se dépense comme un PAIEMENT `AVOIR`** (`OrderPayment`), pas comme une réduction du total : le total de la commande reste entier. Raison : l'émission retire déjà du CA (canal `AVOIR` du remboursement) ; une vraie réduction le retirerait deux fois. Le canal `AVOIR` des stats est donc négatif tant que l'avoir dort. `PAYMENT_MODES` contient `AVOIR` ; `SELECTABLE_PAYMENT_MODES` (sans lui) alimente tout sélecteur d'argent réel (caisse, régularisations, canal de remboursement).
- **`Order.creditApplied`** = avoir actuellement débité pour la commande (rend chaque opération idempotente). Caisse : `setOrderPayment`/`payAndComplete` alignent le débit sur la ligne `AVOIR` (`applyPaymentCredit`) ; dépaiement et annulation le rendent (`releaseOrderCredit`), la reprise d'une annulée le redébite (`reapplyOrderCredit`). La modale d'encaissement le propose (`GET /api/caisse/orders/:id/credit`).
- **En ligne : coupé par défaut** (`CreditSettings.onlineEnabled = false`, Paramètres + MCP). Sans SMS/OTP, le numéro seul ne prouve rien : n'importe qui pourrait consulter ou dépenser l'avoir d'autrui. Coupé, `GET /api/credit-info` renvoie `{0, 0}` **sans lire le client** (réponse identique pour « inconnu », « sans avoir » et « avec avoir » : aucune fuite) et `holdCreditForOrder` ne retient rien (`useCredit` est ignoré **côté serveur**, pas seulement masqué). L'avoir ne se dépense alors **qu'en caisse**, où le personnel voit le client. Réactivé, `onlineDailyCap` (défaut 5 000 F) borne l'avoir dépensé en ligne par client et par jour (`lib/credits/online-cap.ts`, calculé sur le journal : une restitution libère le plafond) et `credit-info` reste limité en débit (`allowCreditLookup`) — mais le risque d'usurpation par numéro demeure : ne le réactiver qu'avec une vraie preuve (code remis par le personnel, passe via la page de suivi). Quand actif : `createOrder` retient l'avoir dès la création (`useCredit`, `holdCreditForOrder`) car il réduit le montant Jèko ; les frais portent sur la part restante. `startJekoPayment` fige `paymentCreditPart` avec `paymentAmountDue` ; `settleJekoTransaction` enregistre `[jèko, AVOIR]`. L'expiration (`expireOrder`) rend l'avoir ; un paiement tardif sur une commande à avoir (`paymentCreditPart > 0`) part en remboursement, comme la fidélité.
- **Caisse : retenu automatiquement à la création** (`holdCreditForCashier`, `lib/credits/spend.ts`, appelé par `createCashierOrder` pour un client identifié ; pas pour une commande antidatée ni à acompte). `Order.creditApplied` est posé, la carte caisse affiche « Avoir client appliqué », et la modale d'encaissement l'ajoute d'office en ligne `AVOIR` (case décochable pour l'écarter : `setOrderCredit` rend alors l'avoir). Annulation / dépaiement le rendent comme avant.
- **Plafond remboursable** (`getRefundCap`) : exclut la part payée par avoir (elle se rend en avoir, pas en espèces/Jèko).
- **Conversion en argent** (`lib/refunds/convert-credit.ts`) : depuis un avoir payé, demande d'un remboursement normal (`creditSourceId`) qui **débite le solde à la demande** et le rend s'il est refusé/annulé. Il sort de l'argent (trésorerie, solde Jèko) mais **ne retire pas de CA une 2e fois** ni n'entame le plafond : les agrégats de CA, le plafond et « remboursée en totalité » filtrent `creditSourceId: null`.
- **Données personnelles** : le solde est exporté (`creditEntries`), l'anonymisation et la purge **refusent** un client qui a un avoir (`CustomerHasCreditError`, `creditBalance: 0` dans la purge) ; la fusion de clients déplace solde, journal et remboursements.
- **Après déploiement** : `pnpm db:push` (migration `20261021090000_add_customer_credit` : enums, `Customer.creditBalance`, `Order.creditApplied`/`paymentCreditPart`, `Refund.creditSourceId`, tables `customer_credit_entry` et `credit_settings` avec `onlineEnabled`/`onlineDailyCap`).

## Assistant IA (OpenRouter)

- **Quoi** : un assistant de chat dans le dashboard (`components/(dashboard)/assistant/`) qui répond et AGIT (créer une dépense, ajuster le stock…) via l'API OpenRouter (`lib/ai/openrouter.ts`, `fetch` direct, pas de SDK). Activé par `OPENROUTER_API_KEY` (optionnelle : absente = bouton masqué, route en 503) ; modèle via `OPENROUTER_MODEL` (défaut dans `lib/ai/config.ts`).
- **Aucune logique métier propre** : `lib/ai/assistant/tools.ts` réutilise le registre MCP (`lib/mcp/tools`), mêmes schémas Zod, mêmes rôles que le serveur MCP (ADMIN/MANAGER tout, COMPTABLE finance, ANALYSTE lecture seule ; les autres rôles n'ont pas l'assistant). Les outils d'image base64 sont exclus, ainsi que `get_menu` (menu entier : dépasse la limite de résultat de 12 000 caractères et fait boucler le modèle) et `toggle_product_availability` (non idempotent) — l'assistant passe par `search_products` (compact, flou) et `set_product_availability`. Nouvel outil MCP = disponible automatiquement.

## Goûts vs suppléments

- `SupplementGroup.kind` : `'flavor'` (goût, dans le produit) ou `'extra'` (supplément, par-dessus ; défaut). Existe pour la cuisine : un goût « Chocolat » et un supplément « Chocolat » ne doivent pas se confondre sur le ticket.
- **Figé sur la ligne de commande** (`CartItemSupplement.kind`, `lib/schemas/order/cart.ts`) comme le prix. Seul `'flavor'` est écrit (`kindStamp`, `lib/supplements/kind.ts`) : absent = supplément, ce qui garde les commandes antérieures lisibles. Tout code qui fabrique une ligne depuis un groupe (`getSelectedSupplements`, `reorder`, `buildOrderItemsFromMenu`) doit passer par `kindStamp`, sinon le champ est perdu.
- `kind` n'a **pas de défaut Zod** : un payload partiel (MCP `update_product`) qui l'omet laisse la valeur en base (`syncSupplementGroups` ne l'écrit que s'il est fourni).
- Cuisine : `SupplementBadges` (`dashboard/preparation/_components/supplement-badges.tsx`) affiche, SOUS chaque ligne d'article (sans répéter le nom du produit), des badges : goûts (couleur primaire) puis suppléments (couleur secondaire, préfixe « + »). Rendu par ligne (`cartId`), non fusionné.

- **Architecture** : `app/api/mcp/route.ts` (mince : POST/GET/OPTIONS) → `lib/mcp/http/` (transport : clé statique, garde-fou de rôle ADMIN/MANAGER/COMPTABLE/ANALYSTE, `?toolset=`, flux SSE, revalidation cache) → `lib/mcp/handler.ts` (dispatch JSON-RPC, agnostique du framework, filtre `tools/list`/`tools/call` par `allowedTools`) → `lib/mcp/tools.ts` (barrel) → `lib/mcp/tools/registry.ts` (registre assemblant un module `McpTool[]` par domaine dans `lib/mcp/tools/`).
- **Règle d'or** : les outils MCP ne dupliquent **aucune** logique métier. Ils branchent `lib/menu.ts` (`getMenuAdmin`) et `lib/menu-mutations.ts`, et réutilisent les schémas Zod existants (`z.toJSONSchema` génère le `inputSchema`). Pour ajouter un outil, étends le module de son domaine dans `lib/mcp/tools/` ; pour un nouveau domaine, crée un module `McpTool[]` **et** ajoute son spread dans `registry.ts` (sinon l'outil est absent de `tools/list`, des gardes de rôle et du filtre `?toolset=`).
- **Images** : la persistance vit dans `lib/uploads.ts` (`saveImage`), partagée par les routes `/api/upload` + `/api/upload/receipt` (multipart, dashboard) et les outils MCP `set_product_image` / `set_expense_receipt` / `set_investment_document` (base64). Toute image reçue (JPEG/PNG/WebP/AVIF/HEIC, max 25 MB — `MAX_UPLOAD_SIZE_BYTES`) est **retraitée avec `sharp`** : auto-orientation EXIF, redimensionnement « inside » `IMAGE_MAX_DIMENSION` (2200 px), ré-encodage **WebP** (`IMAGE_WEBP_QUALITY`), puis écrite en `/uploads/<subdir>/<uuid>.webp`. Les formats/tailles autorisés sont centralisés dans `lib/schemas/upload.ts` (`ALLOWED_IMAGE_MIME_TYPES`, qui ré-exporte `MAX_UPLOAD_SIZE_BYTES` depuis `config/constants.ts`). `imageUrlSchema` accepte un chemin relatif `/uploads/...` **ou** une URL http(s). `update_product` est une mise à jour **partielle** (champs absents = inchangés).
- **Outils en lot** : `bulk_update_products` et `bulk_set_product_stock` (`lib/menu/mutations/bulk.ts`, plafond `BULK_PRODUCTS_MAX`) modifient jusqu'à 100 produits en une transaction : validation complète avant écriture (un id inconnu → rien n'est écrit), `dryRun` pour l'aperçu, **valeurs absolues uniquement** (jamais de `toggle_*`/`restock_*` en lot : un rejeu doublerait l'effet). Une écriture de masse ailleurs suit le même patron ; ne jamais mettre en lot suppression, encaissement, remboursement ni fidélité. `pendingLabel` (`lib/ai/assistant/labels.ts`) libelle ces lots sur la carte de confirmation.
